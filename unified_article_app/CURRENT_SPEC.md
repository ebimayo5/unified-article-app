# Article Compass System 現在仕様メモ

更新日: 2026-05-28

このメモは、今後の修正で古い仕様と混ざらないようにするための基準です。
迷ったら、このファイルを先に確認します。

## 目的

DRIVE BASE、たくみパパ、汎用記事の3つの記事生成システムを、1つのApps Scriptと1つの操作パネルに統合する。

基本方針:

- スプレッドシートは保存場所と候補確認の場所にする
- 実際の入力、生成、コピー、WP下書き作成はパネル中心にする
- DRIVE BASEとたくみパパはSEO記事 + WordPress下書き作成まで行う
- 汎用記事は納品用記事生成のみで、WordPress下書き作成は行わない

## API利用の事前承認ルール

- 新しいAPI利用を追加する場合は、実装前に必ずユーザーへ確認する
- APIを使っていなかったボタンや工程をAPI利用へ変更する場合も、実装前の確認を必須とする
- 既存処理のAPI呼び出し回数を増やす場合や、費用が上がるモデル・品質設定へ変更する場合も同様とする
- 確認時は、目的、対象ボタン・工程、使用APIとモデル、1回または1記事あたりの最大呼び出し回数、費用目安、失敗時の保存・再開方法を先に説明する
- 明確な承認を得るまでは、実装、実生成テスト、push、deployを行わない
- 既存APIの実生成テスト、ブラウザ操作、push、deployも、必要性を説明して最小回数で実行する

## キーワード候補シート

対象:

- DRIVE BASE_キーワード候補
- たくみパパ_キーワード候補

基本列:

| 列 | 内容 |
| --- | --- |
| A | 状態 |
| B | 案件名 |
| C | キーワード |
| D | 検索ボリューム |
| E以降 | 元データ貼り付け用 |

候補シートは、キーワードを広く貼って、次に書く候補を選ぶための場所。

運用:

- 候補シート全体を見ながら書くキーワードを選ぶ
- 案件がある場合は、B列で `案件管理` シートの案件名を選ぶ。案件なしは空欄でよい
- 状態を `書く` にする
- パネルまたはメニューから記事シートへ送る
- 送信後は候補側を `転送済み` にする
- `転送済み` 行はグレー表示にする
- 候補シートの状態は `書く`、`転送済み`、`保留` の3種類だけを使う
- 旧状態 `記事化済み` は表示ルール整備時に `転送済み` へ移行する

汎用記事には候補シートは不要。

## 案件管理シート

シート名: `案件管理`

| 列 | 内容 |
| --- | --- |
| A | 案件名 |
| B | アフィリエイトURL / A8リンクHTML |
| C | ショートコード |
| D | 案件注意点 |

- 候補シートB列のプルダウンは、案件管理シートA列と連動する
- 候補を記事シートへ送る際は、既存の記事列を変えず `D: メイン案件名`、`E: メインアフィリエイトURL`、`F: 案件注意点` へ転送する
- 案件名が空欄なら、D〜Fも空欄のまま転送する
- C列にショートコードがある場合は、B列よりショートコードを優先してCocoon囲みボタンへ設定する
- C列が空欄の場合はB列を使う。通常URLは従来のCTA生成を維持し、A8リンクHTMLはリンク先と計測画像を保持したまま自由テキスト部分だけを記事文脈に合うCTAへ置換する
- A8リンクHTMLの表示文言が `自由テキスト`、`＜自由テキスト02＞` などの明確なプレースホルダーではなく、すでに具体的なCTA文言になっている場合は改変しない
- A8リンクHTMLをB列へ貼った場合は、`href` 内のURLを記事シートE列へ自動抽出する
- 管理CTAでは、AIは本文内の自然な位置と具体的なCTA文言だけを決め、リンクHTML・計測画像・ショートコード・Cocoonボタン構造は本文生成後にシステム側で1回だけ挿入する
- 管理CTAは導入文、「この記事のポイント」、Q&A内には置かない。AIが置換記号を返さなかった場合は「よくある質問」または「まとめ」の前へ補完する
- 案件が検索意図の中心から少し離れる場合も案件を省略しない。ただし案件専用のH2/H3や長い話題転換は作らず、既存の購入判断・選び方セクション内で、変えにくい不満と後から調整できる不満など記事の主題に役立つ短い橋渡しを1〜3段落だけ入れる
- ナビ男くん案件は関連度にかかわらず「ナビ男くん紹介セット」と案件CTAの両方を出す。関連度が高いテーマは対応車種・施工内容へ直接つなぎ、少し離れるテーマは短い橋渡しを作ってから、重複説明を増やさず2つを連続した一つの導線として配置する
- CTAや通常リンクに `rel` 属性が重複した場合は、本文保存・WordPress送信前に1つへ統合し、値も重複除去する。修復後も重複が残る場合はWordPress送信を停止する
- H2は「よくある質問」「まとめ」を含めて基本6〜8個を目安とする。9個でも検索意図・判断材料・役割が異なる場合は無理に統合しない。10個以上は細分化を重点確認し、数ではなく内容が重複するH2だけを統合する。6個未満でも数合わせで不要なH2を増やさない
- 公開前の自動修正では、Cocoonブログカード、CTA、画像、情報ボックス、「この記事のポイント」を保護記号へ退避し、AI修正後に元HTMLを同じ位置へ戻す。保護位置が消失・重複した修正案は不採用とし、元本文・元メタデータを維持して再チェックする
- 同じ案件名が複数ある場合は誤転送防止のため転送を止める

## 画像プロンプト作成

ブラウザ自動操作やOpal/Whisk/ChatGPTへの自動送信は、ログイン状態や画面変更で壊れやすいため正機能としない。手動生成ではChatGPTへ1枚分ずつ貼り付ける。自動生成では、選択中の画像APIで1枚ずつ生成し、WordPressへ途中反映しながら進める。

パネルの `画像プロンプト作成` ボタンで行うこと:

1. タイトル案またはメインキーワードをアイキャッチ用タイトルとして使う
2. 本文HTMLからH2見出しを抽出する。本文内容は画像プロンプトへ渡さない
3. H2ごとに画像必要度を判定する
4. APIを使わず、タイトル・メインキーワード・H2名から各画像の役割、図解型、構図、短い文字、避ける要素を組み立てる
5. アイキャッチ1枚分の画像生成プロンプトを必ず作る
6. A判定のH2は最大6枚まで画像化対象にする
7. B判定のH2は、枠に余裕がある場合のみ最大2枚まで画像化対象にする
8. C判定、FAQ、まとめは画像化しない
9. モーダルには1枚分だけ表示し、前後ボタンで全プロンプトを移動できるようにする
10. `この1枚をコピー` は表示中の1枚だけをコピーし、コピー後は次の画像を表示する
11. `画像生成してWP差し込み` は設計済みの全プロンプトを内部で渡し、記事長に応じて必要な画像だけを画像APIで生成する

H2画像判定:

- A: 比較、違い、手順、流れ、原因と対策、判断基準、選び方、費用内訳、相場、注意点、リスク、チェック項目、メリット/デメリット、失敗/後悔、安全、保証など。読者理解に画像が強く効く。
- B: 具体例、ケース分け、特徴、理由、おすすめ、必要なもの、便利な使い方、種類、パターン、確認ポイントなど。記事の長さやA判定の数に応じて画像化する。
- C: 導入補足、短い共感、FAQ、まとめ、文章だけで十分な説明。

プロンプトの原則:

- 画風指定はプロンプト先頭に独立して置く
- 基本画風は「最新アニメ風」とする
- 画風を変えたい場合は、生成されたプロンプトの `【画風指定】` 行だけを書き換えればよい
- 共通ルール側には画風名を混ぜず、「清潔感ある図解イラスト」など画像の役割・品質だけを書く
- 本文を最大900文字の「本文要約」として画像モデルへ丸投げしない
- 各画像に `画像生成プロンプト` を持たせ、被写体、場面、配置、視点、図解要素を具体化する
- 手動コピーでは1回につき1画像の情報だけを渡し、複数画像を同時依頼しない
- 一度に全部を1枚へまとめる指示はしない
- 同じ構図の使い回しは禁止する
- アイキャッチとH2図解は役割を分ける
- アイキャッチにはタイトル由来の自然なメイン見出しを入れ、必要なら補助文言を1つまで添える
- H2図解にはメイン見出しに加え、図解要素へ2〜8文字程度の短い日本語ラベルを2〜3個まで入れてよい
- 長文説明、記事タイトル全文、H2全文は画像内へ入れない
- 画像の右下隅に対応番号を小さく入れる。アイキャッチは「00」、H2画像は「01」「02」のように2桁で入れる
- 実在ブランドのロゴ、正確な商品パッケージ、人物の顔の特定描写は避ける

## 読者心理メモ

読者心理メモは、本文にそのまま貼る素材ではなく、記事構成へ渡す設計メモとして扱う。

必須の整理:

- 顕在ニーズ
- 潜在ニーズ
- 読者の葛藤
- 導入文で拾う本音
- 見出し順のヒント
- FAQ候補
- 記事で深掘りすると刺さる判断軸
- 主役にしない補足テーマ
- 本文で事実として使わない方がよいもの
- 安全・法規・保証まわりの書き方ガード
- 本文で優先して扱う材料
- FAQに回す材料
- 今回は主役にしない材料

本文生成では、本文で優先して扱う材料を前半H2・比較表・判断軸へ優先反映し、FAQに回す材料はFAQや補足へ回す。今回は主役にしない材料は主軸にせず、必要に応じて内部リンク、関連補足、要確認ポイントへ回す。

## 記事構成作成

本文生成の前に、パネルの `記事構成作成` ボタンで構成メモを作れる。

処理の流れ:

1. 現在の行を保存する
2. 読者心理メモが空なら、先に読者心理メモを取得する
3. メインキーワードから検索結果を取得し、上位候補URLを競合候補として抽出する
4. 競合候補のタイトル、メタディスクリプション、H2/H3/H4、本文冒頭、抽出キーワードを取得する
5. 読者心理メモと競合分析を突き合わせる
6. `構成メモ` 欄へ、本文手前の記事構成まで保存する

構成メモの保存内容:

- 自動競合分析メモ
- 記事作成のヒントに用いた上位URL
- 読者心理から拾った材料
- 競合・参考URLから拾った材料
- 本文に入れる材料
- FAQに回す材料
- 今回は主役にしない材料
- 見出し構成に使った判断
- 本文手前の記事構成（確定H2/H3構成、各セクションで答えること、使う材料、注意点）

注意:

- Apps Script単体ではSeleniumは動かせないため、現時点ではGASの `UrlFetch` による検索結果取得を使う
- 検索結果の取得先はBing/Yahoo検索を使い、取得できる範囲で競合候補を抽出する
- 検索結果取得はブロックやHTML変更で失敗する場合がある
- 競合URL欄は内部保持用として残すが、パネル上には表示しない
- 取得した上位URLは、構成メモの `記事作成のヒントに用いた上位URL` に最大10件まで残す
- 内部保持用の競合URL欄には、互換性のため最大3件だけ自動保存される
- 構成メモ作成時の詳細分析には上位10件まで使う
- 競合URLは本文リンクには使わず、構成分析と不足論点の把握だけに使う
- 将来Seleniumのローカル取得サーバーを作る場合も、出力先は同じ構成メモ欄に揃える
- 本文生成では、事前に作成された構成メモを優先して使う。ただし外部出典、内部リンク、案件条件、安全・法規・保証の制約と矛盾する場合は、事実確認と安全側の表現を優先する

### ローカルSeleniumアプリ連携

`KeywordTreasureFinder.exe` のようなローカルアプリ側で Selenium + Chrome/ChromeDriver を使って検索結果を取得する場合は、Apps ScriptのWebアプリへPOSTして結果を取り込める。

現在は、記事作成システム側からトレファイへ依頼するキュー方式を正とする。GASはローカルPCのEXEやChromeを直接起動できないため、ローカルPC側で `article_bridge.py` を起動し、Webアプリのキューを定期確認する。

記事構成作成の流れ:

1. 記事作成パネルで対象行を読み込む
2. 「記事構成作成」を押す
3. `UA_TREFAI_BRIDGE_ENABLED=true` かつ競合URL欄が3件未満なら、`トレファイ連携` シートへ依頼を登録する
4. ローカルPCの `article_bridge.py` が `get_trefai_job` で依頼を取得する
5. トレファイ既存の `SearchCrawler` で、記事キーワードの上位URLを取得する
6. `complete_trefai_job` で上位URLをApps Scriptへ返す
7. Apps Scriptが競合URL欄へ表示用として最大3件だけ保存し、詳細分析にはトレファイから受け取った上位10件までを使って構成メモを作成する

この方式では、トレファイ本体のGUI/EXEの動きは変更しない。記事作成システム連携は別ファイル `article_bridge.py` で行う。

POST先:

- 統合版Apps ScriptのWebアプリURL

必要なスクリプトプロパティ:

- `UA_LOCAL_IMPORT_TOKEN`: ローカルアプリからの取り込み用トークン
- `UA_TREFAI_BRIDGE_ENABLED`: `true` のとき、記事構成作成でトレファイ連携キューを使う

キュー取得JSON例:

```json
{
  "action": "get_trefai_job",
  "token": "UA_LOCAL_IMPORT_TOKENに設定した値"
}
```

完了JSON例:

```json
{
  "action": "complete_trefai_job",
  "token": "UA_LOCAL_IMPORT_TOKENに設定した値",
  "jobId": "キューから受け取ったjobId",
  "appType": "DRIVE BASE",
  "row": 12,
  "keyword": "カーナビ テレビ 見れない",
  "competitorUrls": [
    "https://example.com/a",
    "https://example.com/b",
    "https://example.com/c"
  ],
  "status": "done"
}
```

トレファイ側から直接取り込む旧方式も残す。これは手動・別アプリ連携用の互換口として扱う。

JSON例:

```json
{
  "action": "import_competitor_analysis",
  "token": "UA_LOCAL_IMPORT_TOKENに設定した値",
  "appType": "DRIVE BASE",
  "row": 12,
  "keyword": "カーナビ テレビ 見れない",
  "competitorUrls": [
    "https://example.com/a",
    "https://example.com/b",
    "https://example.com/c"
  ],
  "competitorAnalysisMemo": "【上位記事で共通して扱われている内容】...",
  "structureMemo": "【読者心理から拾った材料】...",
  "articleOutline": "【確定したH2/H3構成】..."
}
```

取り込み時の動作:

- `row` が指定されていれば、その記事行へ保存する
- `row` がなく `keyword` が指定されていれば、該当キーワードの保存行を探し、なければ新規行を作る
- `competitorUrls` は構成メモの `記事作成のヒントに用いた上位URL` に最大10件まで保存する
- 内部保持用の競合URL欄には、互換性のため最大3件だけ保存する
- `competitorUrls` が4件以上ある場合でも、構成メモ作成時の競合詳細分析には上位10件まで使う
- `competitorAnalysisMemo`、`structureMemo`、`articleOutline` は構成メモ欄へ追記する
- 競合URLは本文リンクには使わず、構成分析だけに使う

## WordPress

### 毎日の自動投稿

- DRIVE BASEとたくみパパは、記事作成パネルでサイトごとに稼働ON/OFF、画像あり/なし、WordPressの到達点（下書きまで/投稿まで）を設定する。`自動投稿設定` シートはサイト別設定の保存先として残す。
- 標準はサイトごとに1日1記事、日本時間の午前4時ごろ。パネルから開始時刻を0〜23時、1日の記事数を1〜5記事の範囲で変更できる。既存設定はDRIVE BASEへ引き継ぎ、たくみパパは初期状態OFFとする。Apps Scriptの時間トリガーのため、開始は数分前後する場合がある。
- 両サイトを同時刻に設定しても並列生成せず、全体で1記事ずつ順番に処理する。案件管理シートは両サイトで共通の1シートを利用する。
- キーワード候補シートの上から最初の `書く` を1件だけ記事管理シートへ転送する。案件名・URL・ショートコード由来の案件情報は既存転送ロジックを使う。
- 読者心理→トレファイ/構成→本文→WP下書き→画像→公開前チェック→1回修正→WP最終反映の順で進む。
- 各段階は保存され、トレファイ待ちやApps Scriptの実行時間制限をまたいで再開できる。
- `公開まで` を選んでも、公開前ルールの重大NG、アイキャッチ未反映、WordPress状態の不整合があれば下書きで停止する。
- 日途中でエラー停止した場合は新しい2件目を開始せず、設定シートに理由を残す。

対象:

- DRIVE BASE: 使用する
- たくみパパ: 使用する
- 汎用記事: 使用しない

現在は公開投稿ではなく、下書き作成まで。

- WordPress下書き作成前に、タイトルの「7つ」「5選」などの数と、対応する本文の見出し・リスト項目数を照合する。不一致なら下書き作成を停止し、公開前修正でタイトルまたは本文を一致させる
- 数字整合、最新公式情報、案件導線の長さと接続理由、CTA HTMLの検査・修正は、DRIVE BASE、たくみパパ、汎用記事の全記事タイプで同じ共通品質ゲートを使う。特定の記事名・車種・住宅テーマへ条件を固定しない

WordPress接続情報はスクリプトプロパティで管理する。

DRIVE BASE:

- `UA_WP_DRIVE_SITE_URL`
- `UA_WP_DRIVE_USERNAME`
- `UA_WP_DRIVE_APP_PASSWORD`
- `UA_WP_DRIVE_CATEGORY_IDS`

たくみパパ:

- `UA_WP_HOME_SITE_URL`
- `UA_WP_HOME_USERNAME`
- `UA_WP_HOME_APP_PASSWORD`
- `UA_WP_HOME_CATEGORY_IDS`

共通設定:

- `UA_WP_DEFAULT_SITE_URL`
- `UA_WP_DEFAULT_USERNAME`
- `UA_WP_DEFAULT_APP_PASSWORD`
- `UA_WP_DEFAULT_CATEGORY_IDS`

注意:

- 通常ログインパスワードではなく、WordPressのアプリケーションパスワードを使う
- REST API制限があると403になる
- Cocoonのメタディスクリプション直接入力は現時点では見送り
- タイトル案は複数出すが、WP下書き作成時は先頭候補をタイトルに使う

現在の方針:

- 外部リンクは数を増やすためではなく、信頼性を補うために使う
- 外部出典シートの候補を優先する
- 候補がない場合でも、URLが確実に分かる公式・公的機関・メーカー公式リンクなら本文に自然に入れてよい
- 「最新」「現在」、経営、倒産、決算、法規、制度、価格など鮮度が必要なテーマでは、本文生成直前に検索エンジンから最新の公式・公的候補を自動検索し、ページの取得状況と日付候補を本文生成へ渡す

- 経営・倒産・決算テーマは、最新IRへの直接リンクと日付付きの具体的な財務数値がそろわない場合、一般論だけで完成扱いにせずWordPress送信前で停止する
- 自動検索で信頼できる公式候補を取得できない場合はURLを推測せず、要確認ポイントへ残して公開を停止する
- URLが不確かな場合は本文に入れず、要確認ポイントに出す
- 競合URL欄に入力されたURLは外部リンク候補ではない。本文中のリンクとして使わず、構成分析・不足論点の把握だけに使う
- 公式ページや店舗公式ページを本文リンクとして使いたい場合は、競合URL欄ではなく外部出典シートへ登録する
- 生成済み本文に外部リンクが入らなかった場合は、`外部リンクを本文へ追加` で本文生成APIを使わずに後入れできる
- 後入れ外部リンクは、外部出典シート候補から関連性が高く、本文にまだ入っていないURLを1件選び、候補の出典名・使う場面・関連キーワードと本文H2セクションを照合して、文脈が近いセクション末尾へ「公式情報で確認する」補足ブロックで入れる

## プロンプト方針

ファイル:

- `prompt.gs`

共通:

- WordPressコードエディターに貼れるHTMLを出す
- H1は使わない
- 導入文のあとに「この記事のポイント」を入れる
- 「この記事のポイント」は通常の見出し＋箇条書きではなく、Cocoonの `tab-caption-box-1` 形式で出す。見出しラベルは `この記事のポイント`、アイコンは `fab-info-circle`、枠線は赤、本文は4〜5項目の箇条書きにする
- ポイント文は、読者がこの記事で得られる判断軸・注意点・比較ポイント・次の行動が具体的に分かる内容にする
- Q&Aのあとに必ずまとめを入れる
- タグは8〜10個を狙う
- 要確認ポイントは最大5個
- AI Overviewに拾われやすいように、H2直下に自己完結した答えを置く
- 表の前後に短い要約を入れる
- 体験談と事実確認が必要な説明は混ぜすぎない
- 実体験がないテーマで、買った・使った・施工した・住んだなどの経験を創作しない
- 実体験がない場合は、公式情報、取扱説明書、メーカー仕様、価格や中古相場、レビュー傾向、店舗・メーカーへの確認ポイント、比較表、読者の条件に置き換えた判断軸で独自性を出す
- 本文では「調べて分かったこと」「比較して見えたこと」「公開前に確認したいこと」「筆者ならここを確認する」という形で、読者の判断を助ける
- DRIVE BASE本文中の一人称は、必要な場合のみ「筆者」を第一候補にし、文脈上自然な場合だけ「私」を使う。「ケイ」は本文中の一人称として使わない

## ナビ男くん紹介セット

- DRIVE BASEの本文に `ナビ男くん` が登場した場合、最初に言及した段落または見出しの直後へ定型の紹介セットを自動挿入する
- 紹介セットは、ナビ男くんの説明、評判記事へのCocoonブログカード、`[affi id=7]` で構成する
- 評判記事URLまたは `[affi id=7]` が本文にすでにある場合は、紹介セットを重複挿入しない
- 生成AIではなく決定的な本文後処理で挿入し、公開前の文脈修正後にも不足時だけ復元する
- 既存本文をWordPress下書きへ送る場合や、WordPress画像を後入れする場合も、送信前に不足時だけ補完してシート本文へ保存する
- たくみパパと汎用記事には自動挿入しない

## アフィリエイトCTA

アフィリエイトリンクは、自然に溶け込ませるだけで終わらせない。読者が「この先に悩みを解決する具体策がありそう」と分かる導線にする。

- アフィリエイト記事では、原則として1記事に1つ程度の囲みCTAを検討する
- 入れる場所は、読者の迷いが整理された直後、向いている条件・注意点・確認ポイントを説明した直後にする
- CTA前には、クリック先で何を確認できるかを1〜2文で説明する
- CTAは通常リンクや独自の囲みHTMLではなく、Cocoonのボタンブロック形式を使う
- ボタン/アンカー文言は曖昧にしない
- 「詳しくはこちら」「公式サイトはこちら」「詳細を見る」「関連アイテムを確認」だけの汎用文言は禁止
- 文言には、案件名またはサービス名と、クリック後の行動を入れる
- 例: `ナビ男くんで対応アイテムを確認する`
- 例: `ナビ男くんで費用と施工条件を確認する`

```html
<!-- wp:cocoon-blocks/button-wrap-1 {"tag":"<a href=\"ここにアフィリエイトURL\" target=\"_blank\" rel=\"nofollow sponsored noopener\">案件名で対応内容を確認する</a>\n","isCircle":true,"isShine":true,"align":"center","backgroundColor":"teal","textColor":"cocoon-white","width":"75"} -->
<div class="wp-block-cocoon-blocks-button-wrap-1 aligncenter btn-wrap btn-wrap-block button-block btn-wrap-circle btn-wrap-shine has-text-color has-background has-cocoon-white-color has-teal-background-color has-custom-width cocoon-block-button__width-75"><a href="ここにアフィリエイトURL" target="_blank" rel="nofollow sponsored noopener">案件名で対応内容を確認する</a></div>
<!-- /wp:cocoon-blocks/button-wrap-1 -->
```

案件管理シートB列がURLのみの場合も、URL文字列を変更せずhrefへ設定し、本文生成後にシステム側で上記Cocoon囲みボタンを生成する。C列のショートコードを最優先し、B列がA8リンクHTMLの場合は自由テキストのプレースホルダーだけをCTA文言へ置換する。既存の具体的なCTA文言、href、計測画像は変更しない。
- 例: `楽天でディテールブラシを比較する`
- 例: `〇〇公式で対応範囲を確認する`
- ただし「絶対おすすめ」「最安」「一番良い」などの断定や、購入を急がせる表現は使わない

DRIVE BASE:

- 車メディア
- 整備士専門学校、整備工場研修、大型トラック運転経験を自然に使う
- 実体験がない車種・用品・施工テーマでは、使ったふりや購入したふりをしない
- 公式仕様、取扱説明書、保証条件、店舗確認ポイント、レビュー傾向、中古価格や費用の見方を整理し、運転者目線・家族利用・中古購入時の判断軸で価値を出す
- 商品提案は売り込みではなく、選ぶときのポイントとして入れる
- 洗車、車内清掃、コーティング、タイヤ、電装品、車中泊用品では、必要に応じて商品カテゴリを提案する
- 2026年5月13日以降の楽天Web Service仕様に合わせ、楽天市場商品検索APIは `UA_RAKUTEN_APPLICATION_ID` と `UA_RAKUTEN_ACCESS_KEY` の両方がある場合だけ使う
- 楽天Web Service側でアプリケーションID、アクセスキー、アプリケーションURLを再設定した値を使う
- GASから楽天APIへ送る場合、`Referer` / `Origin` ヘッダーが必要になるため、スクリプトプロパティ `UA_RAKUTEN_REFERER_URL` または `UA_RAKUTEN_APPLICATION_URL` を楽天側で許可したWebサイトURLと合わせる
- 上記2つが設定されている場合、本文生成後に記事内容から商品カテゴリを自動選定し、楽天市場商品検索APIで取得した商品を楽天アフィリエイトバナーとして自動挿入する
- 楽天バナーの商品数は1件固定にせず、本文文脈に合わせて1〜3件で自動調整する。比較・選び方・定番アイテム・用意するものなど購買検討の文脈では複数候補、補助的な対策では2件、限定的な確認用途では1件を目安にする
- `UA_RAKUTEN_AFFILIATE_ID` が設定されている場合は、楽天APIのアフィリエイトURLを使う
- `UA_RAKUTEN_AFFILIATE_BANNER_HTML` はAPI未設定または取得失敗時の固定バナー fallback として使う
- 楽天バナーは「楽天がおすすめ」ではなく、関連商品カテゴリを比較するための購入先候補として扱う
- バナーはよくある質問またはまとめの前に入れる。導入文、この記事のポイント、Q&A内、まとめの最後には入れない
- 工賃、法規、安全、保証、店舗対応、制度など、商品購入が主な解決策ではない記事では楽天バナーを入れない
- カビ、湿気、後悔、デメリット、故障、不具合などの悩み・予防・注意点系記事でも、除湿機・サーキュレーター・収納用品・清掃用品など、悩み解決に直結する定番アイテムが本文文脈に合う場合は楽天バナー候補にしてよい
- 本文生成プロンプトで提案した定番商品カテゴリは、楽天バナー候補の優先材料にする。商品提案では「読者が検索しやすい一般的な商品カテゴリ名」を本文内に自然に残す
- 楽天の商品リンクやバナーHTMLは本文生成APIに作らせず、本文生成後または後入れ機能でシステム側が挿入する
- パネルでは楽天バナーを「自動判定」「入れる」「入れない」から選べる。保存時はF列の案件注意点へ `楽天バナーあり` または `楽天バナーなし` として反映する
- パネルでは楽天商品検索キーワードを手入力できる。保存時はF列の案件注意点へ `楽天商品キーワード: ...` として反映する
- パネルの候補取得ボタンは、メインキーワード、読者心理メモ、本文、案件注意点から楽天商品検索キーワード候補を最大5件出す
- 楽天候補は「掃除」「収納」など広い単語1語だけで決めない。排水口、ランドリーチェスト、防カビなど具体語との一致を優先し、表記ゆれ（例: ランドリー チェスト / ランドリーチェスト）も拾う
- 案件注意点に `楽天バナーなし` または `楽天なし` と書くと挿入しない。`楽天バナーあり` または `楽天あり` と書くと挿入を優先する
- 案件注意点に `楽天商品キーワード: カーシャンプー 車 洗車` のように書くと、商品検索キーワードを手動指定できる
- 生成済み本文に後から楽天バナーを入れたい場合は、`楽天バナーを本文へ追加` で、商品検索キーワードと本文H2セクションを照合し、読者が商品を欲しくなる文脈（商品提案・選び方・対策セクションなど）の近くへ小リライトとして自然な補足ブロックを追加する。商品数も文脈に合わせて1〜3件で変化させる
- 文脈が近いセクションを判定できない場合だけ、FAQまたはまとめ前へ入れる
- 具体的な商品名、型番、価格ランキングは出典や案件指定がない限り断定しない

- 一人称は「僕」
- 古い実家暮らし、家族、長男の車いす視点をテーマに合う場合だけ自然に入れる
- 家を建てた経験者のようには書かない
- 実体験がない設備・間取り・施工テーマでは、採用したふりや住んだふりをしない
- 古い実家で感じる不便、家族の動線、車いすや家事の視点、公式カタログ、メーカー仕様、口コミの後悔傾向、ショールームや施工会社で確認したいことをもとに、これから家づくりを考える生活者としての判断軸を提示する
- 設備、掃除、収納、家事、外構、防災、子育て、車いす動線では、暮らしの負担を減らす商品カテゴリや設備カテゴリを提案してよい
- 売り込みではなく、暮らしの選択肢として扱う
- 2026年5月13日以降の楽天Web Service仕様に合わせ、楽天市場商品検索APIは `UA_RAKUTEN_APPLICATION_ID` と `UA_RAKUTEN_ACCESS_KEY` の両方がある場合だけ使う
- 楽天Web Service側でアプリケーションID、アクセスキー、アプリケーションURLを再設定した値を使う
- GASから楽天APIへ送る場合、`Referer` / `Origin` ヘッダーが必要になるため、スクリプトプロパティ `UA_RAKUTEN_REFERER_URL` または `UA_RAKUTEN_APPLICATION_URL` を楽天側で許可したWebサイトURLと合わせる
- 上記2つが設定されている場合、本文生成後に記事内容から商品カテゴリを自動選定し、楽天市場商品検索APIで取得した商品を楽天アフィリエイトバナーとして自動挿入する
- 楽天バナーの商品数は1件固定にせず、本文文脈に合わせて1〜3件で自動調整する。比較・選び方・定番アイテム・用意するものなど購買検討の文脈では複数候補、補助的な対策では2件、限定的な確認用途では1件を目安にする
- `UA_RAKUTEN_AFFILIATE_ID` が設定されている場合は、楽天APIのアフィリエイトURLを使う
- `UA_RAKUTEN_AFFILIATE_BANNER_HTML` はAPI未設定または取得失敗時の固定バナー fallback として使う
- 楽天バナーは「楽天がおすすめ」ではなく、暮らしの負担を減らす道具や定番アイテムを比較するための購入先候補として扱う
- バナーはよくある質問またはまとめの前に入れる。導入文、この記事のポイント、Q&A内、まとめの最後には入れない
- 費用、制度、施工、安全、保証など、商品購入が主な解決策ではない記事では楽天バナーを入れない
- カビ、湿気、後悔、デメリット、故障、不具合などの悩み・予防・注意点系記事でも、除湿機・サーキュレーター・収納用品・清掃用品など、悩み解決に直結する定番アイテムが本文文脈に合う場合は楽天バナー候補にしてよい
- 本文生成プロンプトで提案した定番商品カテゴリは、楽天バナー候補の優先材料にする。商品提案では「読者が検索しやすい一般的な商品カテゴリ名」を本文内に自然に残す
- 楽天の商品リンクやバナーHTMLは本文生成APIに作らせず、本文生成後または後入れ機能でシステム側が挿入する
- パネルでは楽天バナーを「自動判定」「入れる」「入れない」から選べる。保存時はF列の案件注意点へ `楽天バナーあり` または `楽天バナーなし` として反映する
- パネルでは楽天商品検索キーワードを手入力できる。保存時はF列の案件注意点へ `楽天商品キーワード: ...` として反映する
- パネルの候補取得ボタンは、メインキーワード、読者心理メモ、本文、案件注意点から楽天商品検索キーワード候補を最大5件出す
- 楽天候補は「掃除」「収納」など広い単語1語だけで決めない。排水口、ランドリーチェスト、防カビなど具体語との一致を優先し、表記ゆれ（例: ランドリー チェスト / ランドリーチェスト）も拾う
- 案件注意点に `楽天バナーなし` または `楽天なし` と書くと挿入しない。`楽天バナーあり` または `楽天あり` と書くと挿入を優先する
- 案件注意点に `楽天商品キーワード: 収納ボックス 住宅` のように書くと、商品検索キーワードを手動指定できる
- 生成済み本文に後から楽天バナーを入れたい場合は、`楽天バナーを本文へ追加` で、商品検索キーワードと本文H2セクションを照合し、読者が商品を欲しくなる文脈（商品提案・選び方・対策セクションなど）の近くへ小リライトとして自然な補足ブロックを追加する。商品数も文脈に合わせて1〜3件で変化させる
- 文脈が近いセクションを判定できない場合だけ、FAQまたはまとめ前へ入れる

汎用記事:

- 案件指示書をA列に入れる
- キーワード候補シートは使わない
- WordPress下書き作成はしない
- 内部リンクは使わない
- 外部リンクは公式・公的・メーカー公式など、信頼性補強の目的で使う
- 楽天アフィリエイトバナーの自動挿入は使わない

## 今後の修正で注意すること

- 似た関数名が多いので、修正前に対象ファイルを確認する
- `config.gs` の列数と、シート側の列数をずらさない
- `汎用記事` にWordPress機能を混ぜない
- 内部リンクは候補を広げすぎるとAIが無視しやすい。関連性のある候補だけ出す
- 外部リンクは出典シート優先。ただし公式URLが確実なら補完してよい
- 競合URLは本文リンクにしない。競合URLを公式確認リンクとして使いたい場合は外部出典シートへ移す
- 商品提案は出してよいが、ランキングや価格の断定は避ける
- コピペ用にApps Scriptへ貼るファイル名とHTMLファイル名の重複に注意する
- コンテキストが長くなったら、この仕様メモを読み直してから作業する
